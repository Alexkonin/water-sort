# Игры

Сборник игр по одной ссылке. Чистый HTML/JS, без сборки, без сервера, без зависимостей.
Открывается меню, из меню — любая игра, из игры кнопкой «☰» — обратно в меню.

| Игра | Что это |
|---|---|
| **Разлей по цветам** | головоломка water sort; уровни генерируются на устройстве и проверяются солвером — все гарантированно решаемы |
| **Защита башни** | классическая оборона: враги идут по дороге, ты ставишь башни вдоль неё; 24 рукотворные карты, на поздних — несколько дорог |

## Файлы

| Файл | Что делает |
|---|---|
| `index.html` | меню: список игр и прогресс по каждой |
| `water-sort.html` | «Разлей по цветам» целиком: логика, генератор, солвер, анимации, интерфейс |
| `tower-defense.html` | «Защита башни» целиком: карты, башни, волны, движок на canvas |
| `shell.css` | общая оболочка меню и «Защиты»: фон, безопасные зоны, шапка, карточки |
| `manifest.json` | описание PWA (имя, иконки, цвета) |
| `sw.js` | офлайн-кэш |
| `icon-192/512/180.png` | иконки для экрана «Домой» |

## Как устроен сборник

Каждая игра — отдельная страница, а не вкладка внутри одной. Причина практическая:
«Разлей» — это две тысячи строк на глобальных именах (`CAP`, `COLORS`, `state`, `$`),
и чтобы ужиться с другой игрой в одном файле, их пришлось бы заворачивать в модули.
Это правка работающей и выверенной игры ради красоты — ровно та цена, которую платить
не за что. Отдельные страницы дают изоляцию бесплатно, а переходы всё равно мгновенные:
service worker держит все страницы в кэше с момента установки.

Поэтому же `shell.css` подключают только меню и «Защита». «Разлей» живёт на своём
встроенном CSS: общая часть там продублирована сознательно, и это записано в самом файле.

**Добавить третью игру** — три места: новый `*.html`, запись в `GAMES` в `index.html`
(иконка, название, описание и функция `progress()`, читающая сохранение игры) и строка
в `ASSETS` в `sw.js`. Меню собирается из списка, а не из вёрстки.

Прогресс у каждой игры свой, в localStorage того же origin: `watersort.v1` и `towerdef.v1`.
Меню читает оба ключа, чтобы показать строчку прогресса на карточке.

## Посмотреть у себя

Нужен локальный сервер: страницы ссылаются друг на друга и на `shell.css`, поэтому
двойной клик по файлу больше не годится (а офлайн-режим и установка на телефон требуют
http/https в любом случае).

Локальный сервер, если нужен полноценный режим:

```bash
python3 -m http.server 8123 --directory "Мои приложения/water-sort"
```

## Как отправить жене

Игра уже выложена: <https://alexkonin.github.io/water-sort/> — GitHub Pages собирает её
из ветки `main`, так что «выложить обновление» = `git push`.

Если нужен другой хостинг — выложить папку целиком и отправить ссылку.

1. Открыть <https://app.netlify.com/drop>
2. Перетащить туда папку `water-sort` целиком
3. Скопировать выданную ссылку и отправить

Ссылка открывается в любом браузере, ничего устанавливать не нужно.
Чтобы ссылка осталась навсегда — бесплатный аккаунт Netlify (кнопка «Claim»).
Альтернативы с тем же результатом: Cloudflare Pages, GitHub Pages, Vercel, Yandex Object Storage.

Отправить одним файлом больше нельзя: страниц теперь несколько, и они ссылаются друг
на друга. Нужна ссылка.

## Поставить как приложение на телефон

Работает только по ссылке (https), не с файла.

- **iPhone:** открыть ссылку в Safari → «Поделиться» → «На экран „Домой“»
- **Android:** меню Chrome → «Установить приложение»

После установки игра открывается на весь экран, без адресной строки, и работает офлайн.
Прогресс хранится в браузере устройства (localStorage).

## Обновление

После любых правок поменяйте номер версии в `sw.js` (`const CACHE = 'games-v25'`),
иначе у тех, кто уже открывал игру, останется старая версия из кэша.

## Как устроена «Разлей по цветам»

- Состояние — массив стеков: `state.tubes = [[0,1,1,2], [2,0,...], [], []]`, числа = индексы цветов.
- `canPour` / `pourCount` / `applyMove` — правила: переливать можно только на такой же цвет
  или в пустую пробирку, и не больше, чем влезет.
- **В пустую льём всегда.** Раньше был запрет «не гонять монолит в пустоту»: одноцветную
  пробирку нельзя было перелить целиком в пустую. Он экономил солверу ветки, но
  **протекал**. Колба с зелёным верхом и «?» под ним отказывала в переливе ровно тогда,
  когда под «?» тоже зелёный, — то есть сам отказ сообщал игроку то, что «?» обязан
  прятать. Это тот же класс утечки, от которого уже защищена отмена хода (она
  возвращает и скрытие тоже), только через другую дверь.
  Солверу отсечка и не нужна: перестановка монолита в пустую той же вместимости даёт
  **то же каноническое состояние**, и `seen` отбрасывает её сам. Цена снятия — генерация
  дорожает с 15 до 20 мс в среднем (худшая 62 → 81 мс), потолок итераций не срабатывает,
  и ни одна раскладка не меняется: сверено на уровнях 1–999, ноль отличий.
- `generateLevel(n)` — раскладка по сиду от номера уровня: у всех игроков уровень N одинаковый.
  Раскладка перемешивается случайно, затем `solvable()` (поиск в глубину с отсечением
  повторов по канонизированному состоянию) проверяет решаемость. Нерешаемые отбрасываются.
- В пробирке 5 слоёв (`CAP`, дублируется в CSS как `--cap`).
- **Палитра.** Соседей по оттенку разводит светлота, а не тон: на слое высотой 19–25 px
  светлотный канал единственный с нормальной разрешающей способностью, и пары,
  разведённые только оттенком, сливаются. Порядок в `COLORS` значим — генератор берёт
  цвета по индексам `0..nc-1`, а `nc` растёт с уровнем, поэтому палитра обязана быть
  хорошей на каждом префиксе, а не только целиком (на 1-м уровне это красный/жёлтый/синий).
  Различимость меряется по **отрисованному** цвету, а не по hex: поверх слоя лежит
  градиент от `rgba(0,0,0,.26)` до `rgba(255,255,255,.20)`, inset-тени и блик `.shine`,
  из-за чего подсвеченный тёмный может совпасть с затенённым светлым. Прошлые
  светло-серый `#c9d2dc` и шифер `#5e7a8c` при базовом ΔE00 28.2 сходились так до **3.5**.
  **Не больше двух цветов на нареченную категорию, и только если разрыв по светлоте
  даёт разное название** (золотой/коричневый, фиолетовый/сиреневый). Двенадцать
  насыщенных цветов не помещаются в десяток категорий, но три оттенка подряд внутри
  одной путаются даже при приличном ΔE: их приходится не различать глазом, а помнить.
  На этом спотыкались обе прошлые версии — у первой было три синих (отсюда слипание
  светло-серого с шифером), у второй три зелёных.
  Текущие показатели против прошлых (CIEDE2000): базовый минимум 20.4 против 14.2 у
  первой и 17.6 у второй, худшая пара на экране 10.3 против 3.5 и 7.7.
  Менять `COLORS` безопасно — раскладки уровней от неё не зависят, генератор оперирует
  индексами (сверено: 999 уровней, ноль изменений). Ещё 8 цветов до двадцати подобраны
  и лежат в истории обсуждения — они понадобятся, если поднимать потолок числа цветов.
- Сложность растёт числом цветов: 3 → 12 к 55-му уровню (до 14 пробирок, 3 ряда).
  Пустых пробирок всегда две.
- **Разная вместимость.** `state.caps[i]` — сколько слоёв вмещает пробирка. С 15-го
  уровня появляются маленькие скляночки на 2 слоя (`SMALL_CAP`), с 30-го — две.
  Они стартуют пустыми и работают как временная полка.
  Важная тонкость: «собранной» (из неё нельзя выливать) считается только
  полноразмерная пробирка — `isSolved` требует `cap === CAP`. Иначе цвет, налитый
  в маленькую доверху, запирался бы в ней и уровень становился нерешаемым.
  При этом победа требует, чтобы каждый цвет лежал целиком в одной полноразмерной
  пробирке, — значит маленькие к финалу всё равно приходится освобождать.
- Порядок пробирок перемешивается (`shuffleTubes`), иначе пустые и маленькие
  выстраиваются хвостом в конце поля. На решаемость перестановка не влияет.
- Пробирки в ряду идут группами по три (элемент `.spacer`) — так поле читается,
  когда их много.
- **Скрытые слои.** С 10-го уровня нижние слои закрыты знаком «?»: `state.hidden[i]` —
  сколько нижних слоёв закрыто. Слой раскрывается, когда становится верхним
  (`revealTops`), а собранная пробирка открывается целиком — иначе не видно, что она
  готова. Глубина: 1 слой на уровнях 10–19, 2 слоя с 20-го. Верхний слой виден всегда,
  поэтому игрок всегда знает, что переливает.
  Уровень остаётся решаемым (солвер видит все цвета) — незнание компенсируется отменой
  хода и запасной пробиркой, как принято в жанре. Отмена возвращает и скрытие тоже,
  иначе через откат можно было бы «подсматривать» цвета.
- Генерация 60 уровней занимает ~60 мс, худший уровень ~4 мс — задержки не видно.

## Параллельные переливы

Ход применяется к модели СРАЗУ (`doMove`), а анимация — только показ. Поэтому можно
затевать следующий перелив, не дожидаясь предыдущего: занятыми считаются лишь две
задействованные пробирки (`state.busyTubes`), остальное поле кликабельно.

Что из этого следует по коду:
- `animatePour` не трогает состояние — состояние источника до хода приходит в `plan`
  (`srcColors`, `startA`, `startB`), иначе параллельные переливы читали бы чужие данные.
- SVG-оверлеи взяты в пул (`acquireSVG`/`releaseSVG`), у каждого свой `clipPath`-id —
  один общий слой два перелива поделить не могут.
- `state.anim` — счётчик переливов в полёте. Кнопки (отмена, +пробирка, подсказка) и
  перестроение поля при resize ждут, пока он обнулится; экран победы (`maybeWin`)
  показывается, когда осядут и переливы, и перелёты на полку.

## Подсказка и тупик

Обе фичи стоят на **трёхзначном** вердикте солвера `solveVerdict` → `'win' | 'dead' |
'unknown'`. Генератору хватало двух значений (и «не нашёл», и «доказал, что нет»
одинаково значат «отбраковать»), но игроку сказать «ты в тупике» можно только на
доказанном `'dead'`: одиночный DFS на комбинаторной задаче имеет тяжелохвостое время,
и ложное обвинение в тупике хуже, чем промолчать. `solvable()` остался обёрткой,
отбраковка раскладок не изменилась ни на уровень.

- **Тупик.** Проверка «легальных ходов не осталось» здесь почти бесполезна: при двух
  пустых колбах ход есть практически всегда — на 270 случайных партий (уровни 60/120/200)
  не встретилось ни одной такой позиции. Настоящий тупик другой: ходы есть, а собрать
  уже нельзя. Из середины партии солвер дёшев (1–3 тысячи итераций, до 145 мс) — часть
  цветов разобрана, пространство состояний схлопнулось. Но 145 мс на главном потоке
  сразу после хода читались бы рывком, поэтому проверка идёт через `requestIdleCallback`
  с задержкой 400 мс: игрок, делающий ходы подряд, её не запускает вовсе.
- **Подсказка.** Первый ход из пути DFS брать нельзя — поиск возвращает первое найденное
  решение, а не кратчайшее, и повёл бы окольной дорогой. Вместо этого легальные ходы
  ранжируются по-игроцки (`rankMove`: завершает колбу → сливает цвета → освобождает
  колбу), и берётся лучший из тех, что сохраняют решаемость. Обычно это первый же
  кандидат, то есть один прогон солвера, ~30 мс.
- **Подсказка опирается на модель целиком, включая скрытые слои** — значит на уровнях
  с «?» её совет косвенно выдаёт то, что они прячут. Это осознанный размен, а не
  недосмотр: инструмент против угадайки в обмен на смягчение механики.
- Обе плашки — `position: fixed`, вне потока. В потоке они пересчитали бы высоту `main`
  и ужали все колбы ровно в момент показа: та же мина, что обходили с полкой.
- Подсветка цели — `outline`, а не `box-shadow`: у `.tube` в тенях лежат внутренние
  рефлексы стекла, перебивать их анимацией значит гасить объём на время подсветки.
- Кнопка заняла место «Дальше». Пропуск уровня дублировался выбором уровня по тапу на
  заголовок, а аварийным выходом с трудного уровня теперь работает подсказка — это важно,
  потому что «+пробирка» с 76-го уровня отключена (см. ниже).

## Потолок поля

`MAX_TUBES = 24` — «+пробирка» на полном поле запрещена. 24 колбы это четыре ряда по
шесть при слое 25px; 25-я уводит в пятый ряд и роняет слой до 18.4px, то есть ужимает
каждую колбу на четверть ради одной лишней. Границ, где лишняя колба добавляет ряд, три
(10→11, 18→19, 24→25), и каждая стоит 26–30% высоты слоя — но запрет стоит только на
верхней. С 76-го уровня поле всегда 24 колбы, значит там кнопка отключена всегда.

## Потолок номера уровня

`MAX_LEVEL = 2000` — предел ручного перехода в поле «номер». Играть можно и дальше:
«Следующий уровень» номер не ограничивает и никогда не ограничивал, потолок стоит
только на вводе. Атрибут `max` у поля ставится из константы (`$('#lvlInput').max`),
чтобы число не жило в двух местах.

Число выбрано не по сложности, а по запасу раскладок. Сложность упирается в потолок
к 76-му уровню: 24 колбы, 12 цветов, два замка, две скляночки — выше расти нечему,
и дальше уровни отличаются только сидом раскладки. Поэтому 2000 — это не «2000
ступеней», а 2000 разных задач на максимальной ступени.

Диапазон 1000–2000 проверен целиком (1001 уровень): нерешаемых нет, собранных на
старте нет, поле нигде не выходит за 24 колбы. Цена генерации совпадает с уже
отгруженным диапазоном 76–999 — по детерминированной мере (итерации солвера, она не
зависит от загрузки машины) медиана 1597 против 1614, p99 8790 против 8114, максимум
17919 против 18127. Все раскладки находятся с первой попытки: ни потолок в 400 попыток,
ни бюджет солвера в 150000 итераций нигде не задеты. Поднимать потолок дальше можно тем
же способом — узкое место не в номере, а в том, что новых механик за 76-м уровнем нет.

## Полка собранных

На уровнях от 11 пробирок собранная пробирка улетает на полосу под шапкой и остаётся
там миниатюрой. Порог считается по числу пробирок, а не по номеру уровня: 11 — ровно
та точка, где `buildBoard` уходит в третий ряд и пробирки начинают мельчать. Значение
замораживается в `state.shelfOn` на старте уровня, иначе «+пробирка» включала бы
механику посреди партии.

Механика чисто презентационная — `canPour`, `pourCount`, `isWin` и солвер не меняются:

- **Триггер только `isSolved`, никогда `isDone`.** У залитой доверху скляночки `isDone`
  тоже истинен, но из неё обязано быть можно вылить обратно (см. «Разная вместимость») —
  улети она на полку, уровень стал бы нерешаемым.
- Пробирка остаётся в `state.tubes` на своём индексе: индексы держат `busyTubes` и
  параллельные переливы, а `isWin` читает ту же модель. Уезжает только DOM-узел —
  настоящий, не клон: `tubeEls[i]` единственная связь модели с DOM.
- Её место в ряду занимает заглушка `.hole` и держит до конца уровня. Ряд не должен
  съезжать: параллельный перелив рисует струю по координатам, снятым в начале своей
  анимации. Стенка у заглушки в 10 раз бледнее стеклянной — её нельзя спутать
  с пустой пробиркой, которая является легальной целью перелива.
- Полоса резервируется с первого кадра уровня. `layout()` меряет живую
  `board.clientHeight`, и полка, вылезающая по первой сборке, пересчитала бы размер
  всех пробирок ровно в момент полёта.
- Размер миниатюры даёт `transform: scale()`, а не подмена `--w`/`--u`: `--wall` и
  `blur()` в `.shine` заданы в абсолютных px и при подмене переменных не ужались бы.
  Побочно конечный кадр полёта совпадает с покоем бит-в-бит — стыка нет.
- Шаг между миниатюрами считается сразу под финальное число собранных, а не под
  текущее: тогда посадка N-й никогда не двигает предыдущие и не портит цель полёта.
  При нехватке ширины миниатюры наезжают друг на друга — 19 штук укладываются в 375px.
- Полёт — FLIP через Web Animations API: сначала DOM приводится к конечному состоянию,
  потом анимируется из инверсии в ничего. `anim.cancel()` даёт синхронный жёсткий стоп,
  поэтому `settleFlights()` перед любой перестройкой поля не требует ожиданий.
  Подскок «щелчок узнавания» вписан в первые кадры полёта, а не сделан классом `.done`:
  два источника анимации на одном `transform` дают непредсказуемый результат.
- Полка — стек, отмена снимает последнюю собранную и всегда в её же заглушку.
  `state.shelf` едет в снимке истории: шорткат «то же число пробирок → только
  перекрасить» состав полки не видит, длина `state.tubes` при уходе наверх не меняется.
- `prefers-reduced-motion` убирает полёт, но не перенос: это смена состояния игры,
  а не украшение.

## Закрытые колбы

С 25-го уровня одна колба закрыта крышкой, с 40-го — две. На крышке замок и число:
сколько колб надо собрать, чтобы она открылась (пороги 2 и 4). Содержимого не видно
вовсе, лить ни внутрь, ни наружу нельзя. Это намеренно другая сущность, чем скрытые
слои «?»: там неизвестен цвет одного слоя, здесь недоступна вся колба — поэтому и вид
принципиально другой, глухая крышка во всю высоту, а не тёмный сегмент внутри стекла.

- **Замок — не состояние, а функция от поля:** `locks[i] > 0 && solvedCount(...) < locks[i]`.
  Отсюда два свойства даром — отмена хода сама возвращает крышку на место (откатили
  ниже порога → снова закрыта), и канонизация состояний в солвере остаётся корректной
  без лишнего измерения.
- **Солвер знает про замки.** `canPour` принимает маску закрытых, `solvable` считает её
  один раз на состояние (внутри `canPour` пересчёт сделал бы проверку решаемости
  квадратично дороже). Раскладка, где порог открытия недостижим на одних лишь открытых
  колбах, отбраковывается там же, где нерешаемые.
- **Порог замка входит в ключ канонизации.** Подписи колб сортируются, и без него
  закрытая колба слилась бы с открытой такого же содержания, а ходы у них разные.
  Ошибка была бы в безопасную сторону (ложное «нерешаемо»), но генерация замедлилась бы.
- Запираются только цветные полноразмерные: скляночка обязана оставаться полкой,
  а пустая — рабочим местом. Число закрытых ограничено так, чтобы порог был достижим.
- В закрытой колбе слои не прячем (`hiddenForLevel` её пропускает): она и так не видна
  целиком, а снятие крышки должно показывать настоящие цвета — иначе двойное наказание.
- Генерация 80 уровней занимает ~0.6 с, худший уровень ~70 мс — вдвое дороже, чем без
  замков, но по-прежнему незаметно: уровень генерируется по одному.

## Анимация перелива

Главная задача — чтобы жидкость реально выливалась, а поверхность оставалась
горизонтальной, а не крутилась вместе со стеклом. Решение — как в игровых движках
(Unity/Godot): поверхность считается в МИРОВЫХ координатах, а форма пробирки лишь
обрезает её.

Как это устроено (функция `animatePour`):
- Вся анимация (подъём → наклон → слив → возврат) идёт единым циклом `requestAnimationFrame`,
  и SVG-жидкость рисуется В КАЖДОМ кадре синхронно с трансформом стекла. Это убирает
  «хлопок» пустой колбы, рассинхрон границ и рывок на входе (раньше подъём был на
  CSS-переходе, а SVG подхватывался только после наклона).
- Пробирка-источник наклоняется **горлышком вниз** (~116–132°) — жидкость скапливается
  у носика и льётся через него; воздушный карман образуется у закрытого дна (вверху).
- Наклонённая колба не вылезает за верх экрана: если её верхняя точка выше поля, вся
  сцена опускается (`TOP`-кламп).
- Струя — широкая лента из самого горлышка (`streamW`), без «кружка» у носика, чтобы
  читалось как слив из колбы, а не капля.
- На время перелива DOM-жидкость источника прячется, а взамен в **SVG-оверлее** (`#pourfx`,
  создаётся один раз) рисуются: полость пробирки как `clipPath` (наклоняется вместе со
  стеклом) и слои жидкости — **горизонтальные полосы** в мировых координатах. Пересечение
  даёт честно горизонтальную поверхность при любом наклоне. SVG — вектор, поэтому чётко
  на ретине и при θ=0 совпадает с DOM пиксель-в-пиксель.
- Уровень слоёв ищется по объёму: `areaBelow` (отсечение полигона полуплоскостью +
  формула шнуровки) и `surfaceForArea` (бинарный поиск уровня). Цвета идут в ОБРАТНОМ
  порядке хранения — верхний (сливаемый) цвет оказывается у носика.
- Струя — SVG-лента (`ribbonPath`, квадратичная безье с сужением книзу и «губой» у носика),
  привязана к нижнему углу горлышка и к поверхности приёмника. Приёмник остаётся на DOM
  (он вертикальный, корректен и так).

Тайминги — константы наверху блока «анимация переливания»: `T_TILT` (наклон),
`T_FALL` (струя летит до поверхности), `T_UNIT` (на один слой), `T_TAIL`. Угол наклона —
`angStart`/`angEnd`, ограничены `fitMax` (чтобы наклонённая пробирка не вылезла за экран).
Геометрия связана с CSS: `TUBE_WALL`, `cavityPolygon` должны совпадать с `.tube`/`.liquid`.

## Как устроена «Защита башни»

Классическая оборона на canvas: дорога задана картой, враги идут по ней от портала
к базе, игрок ставит башни на свободные клетки. Поле 9x13 — пропорция 0.69, ровно
портретная, влезает между шапкой и панелью без прокрутки.

- **Позиция врага — это расстояние в КЛЕТКАХ, а не в пикселях.** При повороте экрана
  и смене размера клетки враги остаются там же, где были; иначе поворот телефона
  посреди волны телепортировал бы их.
- **24 карты заданы руками** — списком путевых точек (`MAPS[i].wp`), между соседними
  точками всегда ортогональный отрезок. Опечатка в координатах даёт не ошибку, а тихо
  кривой уровень, поэтому карты проверяются на старте (`validateMaps`, жалобы в консоль):
  ортогональность отрезков, самопересечения, **касания** (две клетки дороги рядом, но
  не подряд по маршруту — мазок в 0.9 клетки слил бы их в ложную развилку), вход на
  кромке поля, хватает ли места под башни. Длина пути — от 21 клетки до 59.
- **На поздних картах к замку ведёт несколько дорог.** Приток (`branches`) — своя дорога
  от кромки до стыка с главной, дальше по главной до замка. Стык обязан быть ДО замка:
  подход к воротам и кольцо осады считаются по последнему отрезку главной дороги, и
  враг, пришедший в замок с другой стороны, прыгал бы через него в кольцо. Враги
  раздаются по дорогам по очереди, так что игрок получает второй фронт, который нельзя
  закрыть теми же башнями. Притоки у шести карт второй дюжины, у «Крепости» их два.
  Валидатор проверяет и их: стык на главной и не в замке, касание с главной только у
  стыка, между притоками — никогда.
- **Два врага только для поздних карт.** Призрак (с 9-й) не мёрзнет — мороз против него
  пуст, нужны пушка и молния. Голем (с 15-й) в броне 9: пушка первого уровня оставляет
  ему 4 за попадание, молния — единицу; его берут мортира и прокачка.
- **Роли башен разведены бронёй, а не числами.** Броня вычитается из КАЖДОГО попадания,
  поэтому частые слабые удары (молния, 8) по броневику (броня 5) почти бесполезны,
  а редкие тяжёлые (мортира, 30) проходят. Без этого правила все четыре башни свелись
  бы к «урону в секунду за золото», и выбор между ними исчез бы.
- **Мортира стреляет с упреждением** — снаряд летит долго, и без прогноза по быстрым
  целям она не попадала бы никогда.
- **Волны генерируются, карты — нет.** 12 карт x 14 волн руками — это таблица, которую
  невозможно держать согласованной. Вместо неё правило: чем дальше уровень и волна,
  тем больше здоровья и тем раньше входят сложные типы. Характер уровня задаёт карта.

- **Дошедший враг не исчезает, а осаждает.** Первый вариант был жанровой условностью:
  дошёл до замка — снял жизнь и пропал. Теперь враг встаёт у ворот в свободный слот
  полукольца (со стороны, откуда пришёл; кольца уходят назад вдоль дороги, потому что
  дорога всегда на поле, а бок у замка в углу — за кромкой) и бьёт замок с интервалом
  своего типа: ползун раз в 1.4 с по одному, босс раз в 2 с по три. Башни в радиусе
  продолжают по нему стрелять, и стоящая цель — лёгкая. Это меняет стратегию: у ворот
  нужна оборона, и симуляция ставит стража ворот сразу, как сделал бы игрок после
  первого прорыва. Мороз замедляет и удары тоже.
- **Поправка на длину дорог** (`mapFactor`). Длина решает больше, чем номер уровня:
  на короткой дороге врагу негде получить урон, и одна волна на 22 клетках вдвое
  опаснее, чем на 40. Первая дюжина была подобрана вручную так, что поздние карты
  длиннее; во второй короткие карты стоят на поздних номерах, и без поправки
  симуляция роняла их все. Берётся средняя длина по всем дорогам карты (враги
  делятся по ним поровну) против опорных 32 клеток, и только в сторону смягчения:
  длинные карты не ужесточаются, чтобы не сдвинуть выверенную первую дюжину. За 12-й
  картой рост чисел вдвое медленнее — дальше сложность добирается механиками. Прочность замка 20; звёзды — по
  полученным ударам (0 → три, до четырёх → две), а не по дошедшим: дойти и не успеть
  ударить — тоже чисто.
  **У ворот враг — открытая мишень: броня не работает, урон удвоен.** Без этого
  дошедший босс был проигрышем: 3500 HP при броне 6, две пушки у ворот пилят его
  под минуту, а он за это время сносит замок вдвое (симуляция: −26 и −32 на двух
  картах с замком в углу). Теперь прорыв босса стоит около десяти прочности —
  одна звезда, но не конец. Босс у ворот бьёт по одному, как ползун: его цена
  набирается временем, а не силой удара.
  **Замок сам не воюет.** Была версия с лучниками на стенах — чтобы осада имела
  предел даже без башен у ворот. Отвергнута: две стреляющие сущности путают, откуда
  урон и что делать. Правило одно: убивают только башни. Чтобы оно было выполнимо на
  любой карте, все слоты осады лежат в 1.8 клетки от замка — пушка на соседней клетке
  достаёт до любого, — а позиции прижимаются к полю, иначе у замка в углу боковые
  слоты уходили бы за кромку.

### Как это нарисовано

Никаких картинок — всё примитивами canvas, как и колбы в «Разлей» сделаны одним CSS.
Объём даёт одно правило, применённое ко всему: **свет сверху-слева**. Блик там, тень
внизу-справа, под каждым объектом мягкая эллиптическая тень на земле. Три слоя:

- **Статический** (`buildTerrain`) — земля с неровностями, приподнятые плитки под
  башни, камни, дорога (ров-тень, борт, полотно, светлая середина, ~400 камешков
  гравия), замок, виньетка. Рисуется один раз в отдельный canvas при смене уровня или
  размера клетки и потом просто копируется в кадр. Шум — от сида по номеру уровня,
  иначе гравий мерцал бы при каждой перерисовке.
- **Спрайты башен** (`buildSprites`) — корпус каждой из 12 моделей (4 типа x 3 уровня)
  тоже заранее. Уровень меняет модель, а не только числа: у пушки растёт ствол и на
  третьем уровне их два, у мороза больше осколков на орбите, у молнии больше катушек
  и разрядов, у мортиры обручи на стволе; плюс золотые заклёпки на постаменте по
  числу уровней, чтобы уровень читался издалека.
- **Панели обновляются каждый кадр, а не по событию.** Кнопка «Улучшить» держала
  состояние с момента выбора башни: накопил золото во время волны — кнопка так и
  оставалась серой, пока не снимешь и не поставишь выделение заново. Теперь панель
  выбранной башни пересчитывается вместе с показателями, но пишет в DOM только при
  реальном изменении (подпись из типа, уровня и доступности цены покрывает всё, что
  панель показывает). Цена ежекадрового вызова — 1.5 мс на кадр в худшем случае
  (70 врагов, 24 башни, три дороги) против 16.7 мс бюджета.
- **Живое** — стволы (поворот к цели, откат, вспышка, гильзы у пушки, накопление
  заряда у молнии, пульс холода у мороза), враги, снаряды, эффекты, замок. Враги
  рисуются в локальных координатах, где +x — вперёд по дороге: одна функция даёт
  правильный разворот на любом повороте, а градиенты в локальных координатах
  кэшируются. У каждого типа свой силуэт: слизень с глазами и ртом, бегун-капля
  с ногами и шлейфом, броневик с бегущими траками, башенкой и антенной, роевик с
  крыльями, лапками и жалом, призрак с рваным хвостом, голем с трещинами и
  раскалённым ядром.
- **Походка привязана к пройденному пути, а не ко времени** (`GAIT`): шаг совпадает
  со скоростью, замедленный морозом враг и шагает реже. Тень остаётся на земле и
  сжимается-бледнеет, когда тело в верхней точке прыжка, — без этого всё «плыло по
  воздуху». Слизень скачет, бегун семенит, броневик едет, роевик и призрак парят,
  босс и голем идут тяжёлой поступью с облачком пыли на каждом шаге.
- **Босс — один тип в правилах, четыре модели на экране**, меняется каждые три карты
  (`bossSkin`): Огр с рогами и пастью, Рыцарь в кирасе со щитом и плюмажем, Дракон с
  машущими крыльями, хвостом и огненным выдохом, Демон в языках пламени с загнутыми
  рогами. Числа у всех одинаковые — облик не должен ломать выверенный баланс.
- **Замок живой**: рисуется каждый кадр, а не в статике. После удара дрожит с
  затуханием, с потерей прочности покрывается трещинами и теряет средний зубец,
  ниже половины — дымит. Осаждающий при ударе замахивается (разворот корпуса),
  на воротах вспыхивает след когтей и летят щепки.

Цена всего этого: 0.25 мс на кадр в худшем случае (67 врагов, 24 башни) — замер
делался до объёмной графики, после неё запас всё ещё многократный, потому что дорогое
(земля, корпуса) рисуется один раз.

### Как подбирался баланс

Баланс не угадывался, а считался прогонами. На настоящий движок игры (тот же файл,
поверх заглушки DOM) сажался симулированный игрок — «толковый, но не идеальный»:
сначала накрывает башнями всю голую дорогу (включая притоки), потом сравнивает, что
выгоднее за золото — новая башня или прокачка стоящей, считая урон за вычетом
типичной брони уровня; ставит стража у ворот и укрепляет их после первой осады;
строит и во время волны, а не только между. Каждое из этих правил появилось после
того, как его отсутствие роняло уровни, которые человек прошёл бы: прокачка пяти
башен до максимума вместо застройки дороги, короткий приток без прикрытия, тысяча
золота, лежащая без дела к финалу. Дальше все 24 уровня прогонялись целиком и
смотрелось, сколько звёзд он берёт. Такой прогон нашёл и настоящую ошибку: таблица улучшений
индексировалась тремя разными способами в трёх местах, и улучшение башни до 2-го
уровня уронило бы игру у первого же игрока.

Три решения, которые нашлись только прогонами и каждый раз опровергали «очевидное»:

1. **Здоровье считается слагаемыми, а не произведением.** Формула `(1+aL)(1+bW)`
   множит и ПЕРВУЮ волну уровня: на 11-й карте игрок встречал втрое усиленных врагов,
   ещё ничего не заработав, и проигрывал на второй минуте с шестью башнями. Теперь
   `1 + kW*W + kL*L + kX*L*late`: вклад номера карты приходит в основном к концу
   уровня (`late` — доля пройденных волн), поэтому любой уровень начинается посильно.
2. **Расти должно здоровье, а не поголовье.** Доход считается с головы, а угроза —
   со здоровья. Пока росло и то и другое, к финалу карта была уставлена 26 башнями,
   и сложность исчезала. Поголовье придержали, здоровье отпустили.
3. **Босс отнимает 3 жизни, а не 5.** При 5 жизнях вся сложность поздних карт
   сводилась к нему одному: симуляция теряла ровно 10 жизней (два босса) и на 5-м
   уровне, и на 12-м — звёзды перестали различать карты. Теперь прорыв одного босса
   это 2 звезды, двух — одна.

Итог на выбранных числах: симулированный игрок берёт 58 звёзд из 72 и не проигрывает
ни одного уровня — первые шестнадцать карт чисто, последние восемь на одну-две
звезды. Это и есть цель: игру можно пройти, а три звезды на поздних картах требуют
играть лучше среднего. Финал второй дюжины ограничен тремя боссами: четыре по 7000 HP
были стеной — симуляция теряла там по 13–16 прочности при чистых предыдущих волнах.

Худший случай отрисовки замерен: 0.25 мс на кадр при 67 врагах и 24 башнях 3-го уровня —
в 66 раз меньше бюджета кадра, запас есть даже на слабом телефоне.

## Чего здесь нет (осознанно)

Рекламы, покупок, аналитики, серверного прогресса, лидербордов. Всё это добавляется поверх
и требует либо аккаунтов в рекламных сетях, либо обёртки в нативное приложение (Capacitor / TWA).
